# Medicine And Medic Healing Implementation Guide

> **Implementation audit: commit `5e792c7` (2026-07-21).** Phases 1-4 are not implemented. The
> `medic.svg`, `medic_snow.svg`, and `medicine.svg` files remain staged under `C:/z/assets/sprites`
> and are not present in the runtime repository or asset manifest. Generic inventory persistence and
> two stable island centers are useful prerequisites, but medicine definitions, health constants,
> medic placement, protocol, UI, bargaining, dialogue, runtime art, and tests are all pending.

## 1. Purpose

Add two clear, server-authoritative ways to recover health:

1. **Medicine** is a consumable inventory item. One use restores exactly 3 HP, capped at the
   player's maximum HP.
2. **Medic treatment** restores the player to maximum HP after the player accepts and pays a
   server-generated bargain. The requested payment is randomly selected from resources that can be
   acquired on the medic's island.

This guide places exactly two medics: one on the temperate lowlands (the Woods grass island, where
players start and craft early medicine) and one on the Frozen Spire snow island, where thermal
damage makes healing most needed. Each uses environment-matched art (`medic` and `medic_snow`).
Dunes and Marsh get no medic in the first release; their bargain pools below are retained for a
later expansion. Do not place medics on minor islands or the dangerous Core island.

## 2. Current Health Behavior

The current server uses `10` as the player maximum health in several places. Damage comes from
combat, falls, thermal water, weather, hunger, thirst, and boat destruction. Death generally resets
health to 10 and moves the player to a respawn point.

There is already limited passive healing near a campfire in the environment tick:

```js
else if (q.hp < 10 && nearStruct(q, 'campfire', 4)) delta = 1;
```

There is also an implemented `glowcap` consumable that heals 1 HP. Migrate both glowcap and campfire
healing to the same `applyHealing()` helper used by medicine and medic treatment, and retain them in
regression coverage.

The current `init` payload omits restored `hp`, `hunger`, and `thirst`, so an injured reconnect starts
with a client HUD showing hardcoded full values. Medicine implementation must also add `hp`,
`maxHp`, `hunger`, and `thirst` to `init` and test an injured profile reconnect.

That recovery only happens when earlier environmental branches do not apply. Sandstorms,
snowstorms, biome temperature, starvation, and dehydration take precedence. Preserve this passive
campfire regeneration unless balancing explicitly removes it later. Medicine and medics provide
intentional, visible recovery rather than relying on a hidden periodic condition.

The implementation should first centralize health rules because hardcoded `10` values and direct
`p.hp` assignments are currently spread through `server/index.js`.

## 3. Gameplay Rules

### Medicine

- Inventory key: `medicine`.
- Display name: `Medicine` or `Herbal Medicine`.
- Heal amount: exactly 3 HP.
- Never raises health above `MAX_HP`.
- Consumed only when the player is below maximum health and the server accepts the use.
- Cannot revive a dead player after death handling has completed.
- May be used on land, while swimming, in a boat, underground, or inside a shelter unless product
  design later adds an incapacitated state.
- Add a short server cooldown, recommended 750ms, to prevent accidental double-use and packet spam.
- The first version heals only the player using it. Giving medicine to another player can be a
  separate feature with its own targeting and authorization.

Recommended initial recipe:

```js
medicine: {
  cost: { fiber: 4, water: 1 },
  station: 'campfire'
}
```

This makes medicine available early in the Woods without requiring late-game crystal or iron. It
also gives gathered water a second purpose. If the intended asset is alchemical rather than herbal,
an alternative is `{ fiber: 3, crystal: 1 }` at a workbench, but that delays reliable healing until
the Spire/Marsh progression. Choose one recipe and encode it in shared definitions; do not generate
random medicine recipes.

### Medic

- Interact with `E` while within 2.5 world tiles.
- Medic offers a bargain only when the player is injured.
- Successful payment restores health to `MAX_HP`, regardless of missing amount.
- Payment is one stackable resource kind plus an amount in the first version.
- Offer is generated by the server and bound to player, medic, and an opaque offer ID.
- Offer remains stable while open; repeatedly interacting must not reroll it.
- Recommended offer lifetime: 60 seconds.
- Recommended reroll delay after expiry or explicit decline: 20 seconds.
- Payment and healing happen atomically. Never deduct resources unless healing will succeed.
- A player at full health cannot pay accidentally.
- Medic cannot be attacked, pushed, harvested, or used as a building target.
- Recommended: treatment is unavailable for 5 seconds after the player's latest damage, preventing
  medic interaction from becoming unlimited healing during active combat.

## 5. Shared Health And Item Definitions

Add shared constants rather than repeating numeric values:

```js
// shared/defs.js
export const MAX_HP = 10;
export const MEDICINE_HEAL = 3;

export const RECIPES = {
  // existing recipes
  medicine: { cost: { fiber: 4, water: 1 }, station: 'campfire' },
};

export const NAMES = {
  // existing names
  medicine: 'Herbal Medicine',
};

export const emptyInv = () => ({
  // existing inventory keys
  medicine: 0,
});
```

Also add `medicine` to any explicit consumable/item lists. Do not add it to `RESOURCES` if
`RESOURCES` is intended to contain raw crafting resources only. Treat medicine as a crafted
consumable, like `cookedmeat`.

Refactor server health writes through helpers. If guide 06 (damage/death/respawn) is implemented
alongside or before this feature, use its `applyHealing`/`applyDamage` pipeline instead of the
sketches below — they are an earlier draft of the same idea, and guide 06's versions carry the
explicit `heal`/`damage` protocol events. Do not ship both:

```js
import { MAX_HP, MEDICINE_HEAL } from '../shared/defs.js';

function setHealth(p, hp, reason = null) {
  const previous = p.hp;
  p.hp = Math.max(0, Math.min(MAX_HP, hp));
  if (p.hp < previous) p.lastDamageAt = Date.now();
  send(p.ws, { t: 'hp', hp: p.hp, reason });
  return p.hp - previous;
}

function healPlayer(p, amount, source) {
  if (!Number.isFinite(amount) || amount <= 0 || p.hp <= 0 || p.hp >= MAX_HP) return 0;
  const healed = Math.min(amount, MAX_HP - p.hp);
  p.hp += healed;
  send(p.ws, { t: 'hp', hp: p.hp, healed, source });
  return healed;
}
```

Longer-term, route every damage source through `damagePlayer()` so death, respawn, last-damage time,
and health messages cannot disagree. Do not block medicine delivery on that larger refactor if it
would delay the feature, but use `MAX_HP` everywhere touched by this implementation.

## 6. Major-Island And Medic Definitions

Expose stable island identifiers in shared world data:

```js
export const MAJOR_ISLANDS = [
  { id: 'woods',  center: ISLES[0], tile: T.GRASS },
  { id: 'dunes',  center: ISLES[1], tile: T.SAND },
  { id: 'spire',  center: ISLES[2], tile: T.SNOW },
  { id: 'marsh',  center: ISLES[3], tile: T.MUD },
];
```

Only two islands host medics. Define that list explicitly, with the sprite key per medic, and keep
the anchors separate from player spawn, monoliths, notes, mountains, and shorelines:

```js
export const MEDIC_ISLANDS = [
  { islandId: 'woods', sprite: 'medic' },
  { islandId: 'spire', sprite: 'medic_snow' },
];

const MEDIC_ANCHOR_OFFSETS = {
  woods: [10, -8],
  spire: [10, 8],
};
```

Resolve each anchor through a deterministic search for a valid tile:

```js
export function findMedicSpawns(world, landmarkMasks) {
  return MEDIC_ISLANDS.map(({ islandId, sprite }) => {
    const island = MAJOR_ISLANDS.find((mi) => mi.id === islandId);
    const [ox, oy] = MEDIC_ANCHOR_OFFSETS[island.id];
    const [cx, cy] = island.center;
    const [x, y] = findNearestValidTile(cx + ox, cy + oy, (tx, ty, i) =>
      world.tiles[i] === island.tile &&
      !world.nodes.has(i) &&
      !landmarkMasks.movement.has(i) &&
      Math.hypot(tx - cx, ty - cy) > 5
    );
    return { id: `medic-${island.id}`, islandId: island.id, sprite, x, y };
  });
}
```

`findNearestValidTile` does not exist yet and must be added to shared world code. Its scan order is
part of the determinism contract: use a fixed-order ring search (increasing radius, fixed
dx/dy iteration order) with a bounded maximum radius, never `Math.random` or Map/Set iteration
order. If no valid tile exists within the bound, fail loudly in development/tests rather than
silently dropping the medic — an island without its medic is a placement bug, not a fallback.

The final validity function must also avoid:

- Monolith interaction radius.
- Note interaction radius.
- Player spawn clearing.
- Temple and mountain footprints.
- Water and inland lakes.
- Existing authored NPC anchors.
- A narrow tile where structures can permanently trap the medic.

Medics are deterministic world NPCs, not save-file entities. Persist only mutable state if later
features introduce medic death, movement, quests, or limited stock.

## 7. Island-Valid Bargain Pools

The phrase "available on that island" must be represented explicitly. Do not inspect only the
player's current inventory and call that the island pool, because that makes every offer instantly
payable and removes the bargain/search decision. Do not include resources that the current world
generator cannot provide on that island.

Only the `woods` and `spire` pools are reachable in the first release, since those are the only
medic islands. Keep the `dunes` and `marsh` tables defined and tested anyway so a later medic
expansion cannot ship with an unreviewed pool.

Recommended first-pass pools for the current generator:

```js
export const MEDIC_TRADE_POOLS = {
  woods: [
    { resource: 'wood',  min: 6, max: 10, weight: 4 },
    { resource: 'fiber', min: 4, max: 7,  weight: 4 },
    { resource: 'stone', min: 3, max: 5,  weight: 2 },
    { resource: 'meat',  min: 1, max: 2,  weight: 2 },
  ],
  dunes: [
    { resource: 'stone', min: 5, max: 8,  weight: 5 },
    { resource: 'meat',  min: 1, max: 2,  weight: 3 },
    { resource: 'iron',  min: 1, max: 2,  weight: 1 },
  ],
  spire: [
    { resource: 'stone',   min: 4, max: 7, weight: 3 },
    { resource: 'crystal', min: 1, max: 3, weight: 5 },
    { resource: 'meat',    min: 1, max: 2, weight: 2 },
    { resource: 'iron',    min: 1, max: 2, weight: 1 },
  ],
  marsh: [
    { resource: 'fiber',   min: 5, max: 8, weight: 5 },
    { resource: 'crystal', min: 1, max: 2, weight: 2 },
    { resource: 'meat',    min: 1, max: 2, weight: 3 },
  ],
};
```

Important balancing notes:

- `iron` is available only through underground mining on diggable islands. Remove it from a pool if
  the final implementation interprets "island available" as surface resources only.
- Do not request `diamond`, `starmetal`, `essence`, Monolith Cores, medicine, tools, boats, cloaks,
  structures, or quest items in the initial bargain pool.
- Dunes currently do not generate bushes, so do not request fiber there merely because a player can
  carry fiber from Woods.
- Marsh does not generate ordinary stone nodes, so do not request stone there unless generation is
  changed first.
- Revisit these tables whenever world-generation resource rules change. Add a test that every trade
  pool resource has at least one legitimate acquisition source in that island definition.

Select entries with server-side weighted randomness and amounts inclusively between min/max:

```js
function weightedChoice(entries, random = Math.random) {
  const total = entries.reduce((sum, e) => sum + e.weight, 0);
  let roll = random() * total;
  for (const entry of entries) {
    roll -= entry.weight;
    if (roll < 0) return entry;
  }
  return entries[entries.length - 1];
}
```

Gameplay randomness does not need to be deterministic world generation. It must run only on the
server. For reproducible tests, inject a seeded/fake random function into the offer helper.

## 8. Server Offer State

Keep active offers outside the deterministic world and bind them to the connected player:

```js
let nextMedicOffer = 1;
const medicOffers = new Map(); // player id -> offer

function createMedicOffer(playerId, medic, now = Date.now()) {
  const pool = MEDIC_TRADE_POOLS[medic.islandId];
  const rule = weightedChoice(pool);
  const amount = rule.min + Math.floor(Math.random() * (rule.max - rule.min + 1));
  const offer = {
    id: `${playerId}:${nextMedicOffer++}`,
    playerId,
    medicId: medic.id,
    islandId: medic.islandId,
    resource: rule.resource,
    amount,
    createdAt: now,
    expiresAt: now + 60_000,
  };
  medicOffers.set(playerId, offer);
  return offer;
}
```

Do not call `createMedicOffer` unconditionally on every inspect — that would reroll the offer on
each `E` press, violating the offer-stability rule. The inspect handler must reuse the open offer
and honor the reroll delay:

```js
const medicRerollAt = new Map(); // player id -> earliest time a new offer may be generated

function inspectMedic(playerId, p, medic, now) {
  const existing = medicOffers.get(playerId);
  if (existing && existing.medicId === medic.id && existing.expiresAt > now)
    return existing; // stable while open
  if (existing && existing.expiresAt <= now) {
    medicOffers.delete(playerId);
    medicRerollAt.set(playerId, now + 20_000);
  }
  if ((medicRerollAt.get(playerId) || 0) > now) return null; // reply with 'rate-limited'
  return createMedicOffer(playerId, medic, now);
}
```

Explicit decline deletes the offer and sets the same 20-second `medicRerollAt` entry. An open offer
bound to a different medic may be replaced immediately (the player has physically traveled to
another island), but must not be replaced by re-inspecting the same medic. Clear both maps on
player disconnect.

Do not send internal timestamps or player IDs unless the UI needs them. Return a safe projection:

```js
const publicOffer = (offer) => ({
  id: offer.id,
  medicId: offer.medicId,
  resource: offer.resource,
  amount: offer.amount,
  expiresInMs: Math.max(0, offer.expiresAt - Date.now()),
});
```

Clean offers on player disconnect. Offers do not need persistence in the first version. In the
future room architecture, scope medics and offers by `worldId`; never use one process-global medic
state across rooms.

## 9. Server Protocol

Client requests an offer:

```json
{ "t": "medic", "medicId": "medic-woods", "action": "inspect" }
```

Server responds:

```json
{
  "t": "medicOffer",
  "medicId": "medic-woods",
  "offer": {
    "id": "player1:17",
    "resource": "fiber",
    "amount": 6,
    "expiresInMs": 60000
  },
  "hp": 4,
  "maxHp": 10
}
```

Client accepts:

```json
{
  "t": "medic",
  "medicId": "medic-woods",
  "action": "accept",
  "offerId": "player1:17"
}
```

Result:

```json
{
  "t": "medicResult",
  "ok": true,
  "medicId": "medic-woods",
  "paid": { "resource": "fiber", "amount": 6 },
  "hp": 10,
  "healed": 6
}
```

Failure results should use stable machine-readable reasons:

- `full-health`
- `dead`
- `too-far`
- `wrong-level`
- `in-combat`
- `offer-expired`
- `offer-mismatch`
- `insufficient-resource`
- `unknown-medic`
- `rate-limited`

## 10. Server Medic Validation

Every inspect and accept request must validate:

1. Medic ID exists in the current world.
2. Player is on surface level `z === 0`.
3. Euclidean distance to authoritative medic coordinates is at most 2.5.
4. Player HP is greater than zero and below `MAX_HP`.
5. Player has not taken damage within the configured combat lockout.
6. Request cooldown has elapsed.
7. On accept, offer belongs to this player and medic, matches ID, and is not expired.
8. Inventory amount is sufficient at the moment of acceptance.

Atomic acceptance example. It assumes checks 1-3, 5, and 6 (medic existence, level, distance,
combat lockout, request cooldown) already ran in the shared `medic` message guard; the health and
offer checks must still happen here, immediately before the deduction. The `p.hp <= 0` guard is
required even though `healPlayer` also refuses dead players — without it, the deduction on the next
line would take payment and `healPlayer` would return 0, charging a dead player for nothing:

```js
function acceptMedicOffer(playerId, p, medic, offerId, now) {
  const offer = medicOffers.get(playerId);
  if (!offer || offer.id !== offerId || offer.medicId !== medic.id)
    return medicFailure(p, medic.id, 'offer-mismatch');
  if (offer.expiresAt <= now) {
    medicOffers.delete(playerId);
    return medicFailure(p, medic.id, 'offer-expired');
  }
  if (p.hp <= 0) return medicFailure(p, medic.id, 'dead');
  if (p.hp >= MAX_HP) return medicFailure(p, medic.id, 'full-health');
  if ((p.inv[offer.resource] || 0) < offer.amount)
    return medicFailure(p, medic.id, 'insufficient-resource');

  const missing = MAX_HP - p.hp;
  p.inv[offer.resource] -= offer.amount;
  const healed = healPlayer(p, missing, 'medic');
  medicOffers.delete(playerId);
  sendInv(playerId, p);
  send(p.ws, {
    t: 'medicResult', ok: true, medicId: medic.id,
    paid: { resource: offer.resource, amount: offer.amount },
    hp: p.hp, healed,
  });
}
```

JavaScript's single-threaded event handler makes the synchronous validation/deduction sequence
atomic within one process. With future Postgres-backed room services, perform payment and health
update in one transaction and use offer ID as an idempotency key.

## 11. Medicine Use Handler

Extend the existing `use` branch rather than adding a client-authoritative HP operation. The
current handler in `server/index.js` has no cooldown at all, so keep the 750ms check scoped to the
medicine branch; a top-of-branch check would silently rate-limit the existing water and cooked-meat
paths (including blocking a drink for 750ms after using medicine). If a shared consumable cooldown
is wanted, add it deliberately with its own test, not as a side effect. Initialize
`lastUseAt: 0` wherever the player object is created and restored so the comparison never sees
`undefined`:

```js
else if (m.t === 'use') {
  if (m.k === 'medicine') {
    if (now - p.lastUseAt < 750) return;
    if (p.inv.medicine < 1)
      return send(ws, { t: 'useResult', ok: false, k: 'medicine', reason: 'none-owned' });
    if (p.hp <= 0)
      return send(ws, { t: 'useResult', ok: false, k: 'medicine', reason: 'dead' });
    if (p.hp >= MAX_HP)
      return send(ws, { t: 'useResult', ok: false, k: 'medicine', reason: 'full-health' });

    p.lastUseAt = now;
    p.inv.medicine--;
    const healed = healPlayer(p, MEDICINE_HEAL, 'medicine');
    sendInv(id, p);
    return send(ws, {
      t: 'useResult', ok: true, k: 'medicine',
      healed, hp: p.hp, maxHp: MAX_HP,
    });
  }

  // Existing water and cooked-meat handling follows.
}
```

Do not consume medicine when HP is full. At 9 HP, consume one medicine and report `healed: 1`, not
3. The item always restores up to three; it does not create overheal or a shield.

## 13. Client Interaction Priority

Medic interaction should occur before nodes and water collection, otherwise a nearby tree or lake
can steal the `E` key. In `interact()` use this priority:

1. Exit/interior-specific actions.
2. Mine entrance/shelter transitions.
3. Medic and other authored NPCs.
4. Notes.
5. Resource nodes.
6. Monolith.
7. Water collection.

Example:

```ts
const medic = this.nearestMedic(2.5);
if (medic) {
  this.send({ t: 'medic', medicId: medic.id, action: 'inspect' });
  return;
}
```

The client distance check is convenience only. The server repeats it authoritatively.

## 14. Medic Offer UI

Use a small modal or dialogue panel, not a transient toast, because the player must understand and
accept a cost.

Required content:

```text
Medic
"I can mend every wound, but supplies are scarce."

Current health: 4 / 10
Treatment: restore to 10 / 10
Requested payment: 6 Fiber
You carry: 9 Fiber

[Accept treatment] [Decline]
```

UI behavior:

- Disable Accept when current inventory is insufficient.
- Display offer expiry only if it improves clarity; a progress bar is unnecessary.
- On `offer-expired`, close or refresh through an explicit button. Do not automatically spam a new
  inspect request each frame.
- Escape closes the panel but does not reroll the server offer.
- If the player walks out of range, close the panel and let the server reject any late acceptance.
- After success, update health/inventory from server messages and show the amount paid/healed.
- Use `textContent` or safely escaped strings for server-provided names and quantities.

The medicine item belongs in both inventory and quickbar alongside water/cooked meat:

```ts
for (const k of ['water', 'cookedmeat', 'medicine']) {
  // render data-use slot when count > 0
}
```

The DOM UI cannot use a Phaser texture key directly. Either use a small safe `<img
src="/sprites/medicine.svg">` icon contract or retain an emoji/text icon until the inventory icon
system is upgraded.

## 15. Feedback And Animation

Medicine use:

- Short drink/bandage action, approximately 500-700ms.
- Green/gold three-particle burst or brief glow, not a large combat effect.
- Health HUD pulses once.
- Sound plays only after accepted `useResult` or uses prediction with rollback-safe behavior.

Medic treatment:

- Medic faces the player if NPC facing is supported.
- 1-1.5 second treatment gesture after acceptance.
- Player rig uses a brief idle/rest pose.
- Healing effect appears only after server success.
- Remote clients do not need inventory/payment information. If treatment should be visible, broadcast
  a privacy-safe `{ t: 'medicAnim', playerId, medicId }` event without the paid resource.

Do not delay the authoritative HP update until animation completion. Update server state immediately,
then play presentation. This avoids disconnects or attacks creating inconsistent treatment state.

## 17. Persistence And Multiplayer

- Add `medicine` to `emptyInv`; existing profile snapshots already persist `inv`, so it will persist
  automatically after schema/default handling is correct.
- When restoring old profiles, merge into a fresh `emptyInv()` as the current server does so missing
  `medicine` defaults to zero.
- Medic positions are deterministic/static and need no save entry.
- Offers are per player. One player's offer cannot be accepted by another player.
- One player's payment does not deplete medic stock in the first version.
- Medic treatment changes only the requesting player's HP and inventory.
- In the future room architecture, include `worldId` in medic and offer lookup keys.
- For Postgres persistence, store durable inventory/health changes transactionally at normal profile
  save boundaries; offer state can remain Redis/in-memory ephemeral unless reconnecting to the same
  offer is a product requirement.

## 18. Abuse And Edge Cases

Handle all of these explicitly:

- Medicine use at full health: reject and retain item.
- Two medicine packets in the same frame: cooldown permits at most one.
- Medicine use at 8/9 HP: heal only missing health and consume one.
- Player takes damage while medic modal is open: acceptance revalidates combat lockout and HP.
- Player reaches full HP from campfire before accepting: reject payment.
- Inventory changes after offer generation: acceptance checks current amount.
- Offer replay after success: offer has been deleted; reject without charging.
- Offer accepted from another medic or far away: reject.
- Offer expires while acceptance is in flight: server time wins.
- Disconnect after payment: health and inventory mutation occur in the same synchronous operation and
  are captured by normal profile snapshot/save behavior.
- Player dies near medic: normal death/respawn completes; stale offer is deleted.
- Multiple medics in range due to a placement error: choose nearest, then stable ID as tie-breaker.
- Minor-island classification: no medic and no bargain pool.
- Dunes and Marsh: no medic in first release; requests naming `medic-dunes` or `medic-marsh` fail
  with `unknown-medic`.
- Core region: no medic in first release.

## 22. Acceptance Criteria

- Medicine is craftable, visible, persisted, and heals exactly up to 3 HP per consumed item.
- Medicine is never consumed at full health and never creates overheal.
- Two deterministic medics are accessible on valid terrain: lowlands (Woods) and Frozen Spire, each
  rendered with its environment-matched sprite.
- Medic treatment restores the player completely only after a successful server-authoritative trade.
- Bargains request only resources legitimately available on that medic's island.
- Offers cannot be freely rerolled, replayed, forged, accepted remotely, or used by another player.
- Inventory deduction and full healing are atomic.
- Local UI clearly shows cost, carried amount, and resulting full heal.
- Existing campfire healing, damage, death, persistence, and multiplayer synchronization continue to
  work.
- Automated tests cover success and every rejection path before the feature is marked complete.
